# v4：中断驱动 vs 用户态 spidev 轮询，实测对比

**结论**：系统空闲时，用户态轮询也能用，但采样时刻的抖动是驱动方式的 4.5 倍，并且因为用户态定时器和芯片时钟不同步，总会有约 0.2% 的样本读重或漏掉。CPU 满载以后差距迅速拉大：普通调度的轮询程序在重负载下只剩 702 Hz，六成样本丢失；改用 SCHED_FIFO 能撑住，但抖动和丢样仍明显上升。中断驱动 + IIO 缓冲区在所有负载下都保持 1000.9 Hz、0 丢样，间隔标准差不超过 5.3 µs。

## 测试环境

| 项 | 值 |
|---|---|
| 板子 | 正点原子 ALPHA V2.4，i.MX6ULL 单核 Cortex-A7 792 MHz，512 MB |
| 内核 | 4.1.15（正点原子教程源码），`CONFIG_PREEMPT=y`，`HZ=100`，NFS 根文件系统 |
| 传感器 | ICM-20608-D，SPI 1 MHz，内部采样 1 kHz，DLPF 开 |
| 时长 | 每组 10 s，目标 1000 Hz |
| 负载 | **轻**：2 个 shell 死循环 + 1 个 `dd if=/dev/zero of=/dev/null`<br>**重**：8 个死循环 + dd + 通过 NFS 循环读文件（网卡中断、协议栈同时繁忙） |
| 脚本 | `test/load.sh start\|heavy\|stop` |

## 两种方式

- **驱动（v3）**：芯片每采完一个样本就拉 INT 脉冲 → GPIO 中断上半部记录时间戳 → 线程化下半部 SPI 读 14 字节 → IIO 缓冲区（2048 条）→ 用户程序批量读。测量程序 `test/iio_buffer.c`，间隔取自**硬中断里记录的时间戳**。
- **用户态 spidev 轮询**：IMU 节点交给通用 spidev 驱动（测试专用设备树 `imx6ull-alientek-emmc-spidev.dts`），用户程序用 `clock_nanosleep(TIMER_ABSTIME)` 每 1 ms 醒来，通过 `/dev/spidev2.0` 读 14 字节。测量程序 `test/spidev_poll.c`，间隔取自**每次读完的时刻**；可选 SCHED_FIFO 50 + mlockall。

## 分析

1. **时钟不同步是轮询的固有问题**。芯片实测 1000.9 Hz，用户态定时器 1000.0 Hz，两者慢慢错开：有时一个周期里芯片出了两个样本（漏读），有时一个都没出（重复读）。即使系统空闲（C 组）也有 0.17%。中断方式由芯片决定"什么时候有数据"，不存在这个问题。
2. **普通调度在重负载下崩溃（D2）**。10 个进程抢一个核，轮询程序要排队等时间片；`HZ=100` 下一个时间片 10 ms，p99 正好落在 10.0 ms。程序越来越落后于计划时间（最多落后 4.6 s），1 万次读用了 14.2 s。轻负载（D）没崩，是因为 CFS 会优先唤醒长时间睡眠的任务。
3. **SCHED_FIFO 能救急，但不彻底（E、E2）**。唤醒延迟从 72.8 µs 降到 21.7 µs（轻负载），但 E 组唤醒延迟最大 250 µs，间隔最大却有 1713 µs，说明程序准时醒来后，某次 SPI 传输本身又被拖慢了 1 ms 以上：用户线程是实时的，不代表整条 SPI 路径都是实时的。
4. **驱动方式抖动小，是因为时间戳在硬中断上半部记录**。即使下半部和用户进程被负载拖慢，时间戳记录的仍是"芯片发出中断"那一刻；IIO 缓冲区（2048 条，约 2 s）吸收了用户进程的调度延迟，所以 B2 的 sd 只有 5.3 µs，且 0 丢样。

## 局限与注意

- **CPU 占用不可信，未用于结论**。内核是 `CONFIG_TICK_CPU_ACCOUNTING`、`HZ=100`，CPU 时间每 10 ms 抽样一次；每次读传感器只有几十 µs，大部分落在抽样点之间，所以空闲组统计出 0%~2%。要准确对比需打开 `CONFIG_IRQ_TIME_ACCOUNTING` / `VIRT_CPU_ACCOUNTING_GEN`，或测负载进程的吞吐量。
- 两种方式的"间隔"含义略有不同：驱动方式是中断时刻的间隔，轮询方式是读完时刻的间隔。二者都代表"每个样本被打上的时间有多准"。
- 漏读按标称 1000 Hz 估算，芯片实际快 0.09%，10 s 内会少估约 9 个。
- 每组只跑一次，10 s；负载是人工构造的，真实系统的负载形态不同。
- 驱动方式的缓冲区深度 2048 条：如果读取进程被饿死超过约 2 s，仍会溢出丢数据。
