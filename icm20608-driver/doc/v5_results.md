# v5：硬件 FIFO，实测对比

**结论**：v5 不再每个样本中断一次，改由实时内核线程定时从芯片 FIFO 批量读取。1 kHz、每批 10 个时，中断从 5013 次/s 降到 1553 次/s，上下文切换从 8026 次/s 降到 1286 次/s；每批 24 个时降到 766 和 512。抗延迟能力从 1 个采样周期提高到 26 个：比读取线程优先级更高的实时任务每秒占满 CPU 20 ms 时，v3 丢 2% 的样本，v5 一个不丢。超出 FIFO 容量时（每秒占满 50 ms），v5 也会丢，但每次溢出都被检测到并计数。代价是时间戳变成推算值，绝对误差上限为一个采样周期。

## v5 做了什么

| | v3（`fifo=0`） | v5（默认） |
|---|---|---|
| 数据通路 | 每个样本一次数据就绪中断；线程化下半部读 0x3B 起的 14 字节数据寄存器 | 打开芯片 512 字节 FIFO（每样本 14 字节，能存 36 个）；不开中断 |
| 谁来读 | 中断线程（SCHED_FIFO 50） | 驱动自己的内核线程 `icm20608-fifo`（SCHED_FIFO 50），高精度定时器按绝对时间每 watermark 个采样周期醒一次：读 `FIFO_COUNT`，再一次 SPI 传输读出全部完整样本 |
| 读取期限 | 下一个样本到来之前（1 kHz 时 1 ms） | FIFO 写满之前：(36 − watermark) 个周期 |
| 丢样 | 无法察觉，只能事后从时间戳间隙推断 | FIFO 放不下下一个样本时复位，计入 `fifo_overflows` |
| 时间戳 | 中断上半部记录，每个样本一个 | 按芯片实际周期推算（见分析第 3 条） |
| 批大小 | — | `buffer/watermark`，经 `hwfifo_set_watermark` 传给驱动，上限 24；`buffer/hwfifo_*` 属性按内核 ABI 文档导出 |

ICM-20608 没有 FIFO 水位中断（同系列的 ICM-20602 才有 `FIFO_WM_TH`），所以用定时器代替。读取线程与软件缓冲区的 watermark 对齐：用户态的 poll/read 每批只被唤醒一次。缓冲区记录格式与 v3 完全相同（FIFO 里的字节顺序就是数据寄存器的顺序），守护进程和测试程序都不用改。

对照：本内核（4.1.15）里的主线 `inv_mpu6050` 驱动也读 FIFO，但仍然每个样本一次数据就绪中断，在中断里读 FIFO，并为每个中断记一个时间戳。FIFO 在那里只用来容忍延迟，没有用来减少中断。

## 方法

同一内核、同一测试程序，`insmod icm20608.ko fifo=0` 加载 v3，`fifo=1`（默认）加载 v5。每组 10 s（E 组 60 s），全部 7 个通道和时间戳，`test/iio_buffer <采样率> <秒> 0 <watermark>`。脚本为 `test/v5_bench.sh`，原始输出在 `doc/data/v5_bench.txt`。

- 中断次数/s、上下文切换/s：取自 `/proc/stat` 的 `intr`、`ctxt`，是整机的总数（包括 100 Hz 时钟节拍、网卡等）。
- 丢样：相邻时间戳间隔超过 1.5 个周期就按间隔折算丢失个数（与 v4 相同）。
- 数据检查：板子静止，每个样本的加速度模长应为 1 g 左右。FIFO 一旦读错位，数据会被当成别的通道，模长立刻离谱。所以统计模长不在 0.8–1.2 g 范围内的样本数。
- 负载：`test/load.sh heavy`（8 个死循环 + dd + 经 NFS 循环读文件，同 v4）。`test/rt_hog <ms>`：SCHED_FIFO 60（高于两种读取线程的 50），每秒空转占满 CPU 若干毫秒，期间读取线程得不到运行（硬中断照常）。
- CPU 忙碌率：本内核按时钟节拍采样统计 CPU 时间（`TICK_CPU_ACCOUNTING`，未开中断时间统计），1% 量级的差别分辨不出来（v3、v5 空闲时都在 0.7–1.3% 之间波动），所以开销用中断和上下文切换次数衡量。

## 分析

1. **开销按"批"计，不再按"样本"计**。由 A3、A4 两组线性推算，与 IMU 无关的基础中断约 200 次/s。扣除后，v3 每个样本约 5 次中断、8 次上下文切换，大致来自：数据就绪中断、SPI 控制器的中断，中断线程和读者的唤醒，以及等待 SPI 传输完成时的睡眠和醒来。v5 每批的开销与此相当（每批约 13 次中断、9–11 次上下文切换），但 watermark 10 时批数只有样本数的十分之一。watermark 1 时每个样本一批，还多一次读 `FIFO_COUNT` 的传输，比 v3 略差（A2）。所以 FIFO 本身不省开销，攒批才省。100 Hz 时（D）中断从 508 降到 209 次/s，此时剩下的大部分是与 IMU 无关的时钟节拍和网卡中断。

2. **抗延迟：期限从 1 个周期变成 (36 − watermark) 个周期**。v3 在读取线程被占用 x ms 时几乎丢 x 个样本（C 组每次约 4、20、50 个）。数据寄存器只能存一个样本，晚了就被覆盖。v5 watermark 10 能容忍约 26 ms：5 ms、20 ms 都不丢。50 ms 超出了容量，每次占用溢出一次（10 次占用对应 10 次溢出），每次丢约 29 个。v5 溢出时先读出 FIFO 里完整的 36 个样本再复位（`FIFO_MODE=1` 让芯片满了停写，不覆盖，样本边界不乱），而主线 4.1 的做法是整个 FIFO 丢弃。按 FIFO 容量估算，每次应丢 14–24 个，实测偏多，原因还没有查清。watermark 越大开销越小，但容忍的延迟越短，二者需要权衡：24 时只剩 12 个周期的余量。

3. **时间戳：推算值，误差有界**。一批样本只知道"读的时候 FIFO 里有 n 个"。驱动用"经过时间 / 样本数"长期估计芯片的实际周期（误差小于 1 个周期 / 样本数，越久越准，实测与 v3 一样是 1001.0 Hz，即芯片比标称快约 0.1%），按这个周期接着上一批往后排。再利用一个必然成立的约束修正：最新的样本一定采于 (读计数前的时刻 − 1 个周期, 读计数后的时刻] 之内，排出来超出这个窗口就把这一批均匀拉伸或压缩到窗口边上。所以时间戳单调，绝对误差不超过一个周期（100 Hz 时 10 ms），也不会累积。代价是间隔不再反映真实的采样抖动。实际采样由芯片时钟决定，本来就没有 CPU 带来的抖动。修正发生时间隔会有偏差：D2 的间隔 sd 为 47.7 µs，最大偏差约 0.28 ms，主要出现在刚开始、周期估计还不准的时候；E3 运行 60 s，sd 为 0.7 µs。
   - 发现并改掉的错误：最初只在读完计数后取一次时间。实时任务占用 20 ms 的那组，FIFO 没有溢出，却统计出 24 个"丢失"样本，间隔最小 0.42 ms、最大 2.6 ms。原因是读取线程有时恰好在读完计数、取时间之前被抢占，取到的时刻晚了十几毫秒，整批被错误地拉长。改为在读计数前后各取一次后，同一组为 0（C 表）。

4. **重负载与 SPI 消息泵：推断，未能复现**。第一轮重负载下 v5 溢出了一次，说明实时的读取线程被拖住了 40 ms 以上，而普通进程的负载不该造成这种情况。读 4.1 的 `drivers/spi/spi.c` 发现：每次传输结束后，"队列空了、关闭硬件"的收尾只在 SPI 控制器的消息泵线程（`spi2`）里做。这时如果有新的 `spi_sync()` 到来，传输会被推迟给这个线程执行，而它默认是普通优先级（SCHED_OTHER，nice 0）。重负载下，它在收尾途中被抢占，实时线程就要等它，这是一个优先级反转。新内核为此提供了让 SPI 设备申请实时消息泵的机制，4.1 没有。所以驱动加载时把消息泵改为 SCHED_FIFO 50（模块参数 `spi_rt`，默认开，卸载时恢复）。但对照实验没有复现问题。把所有重负载数据加起来：v5 在消息泵为普通优先级时共跑了 670 s，只有第一轮那 1 次溢出（E3、L1、L3 都是 0）；改为实时后共 370 s，0 次。v3 在普通优先级下共 370 s，丢了 2 个样本（第一轮 B1、L4 各 1 个，都是单个周期的延迟）；改为实时后共 70 s，0 个。这只是"有一点迹象"，次数太少，时长也不对等，不能下结论。所以这个修改只是按代码分析做的预防，不能证明第一轮那次溢出就是它引起的。v4 报告里"SCHED_FIFO 的用户线程准时醒来，SPI 传输本身却被拖慢 1 ms 以上"的现象，也可能是同一原因，同样未经证实。

5. **数据没有错位**。全部 18 组、约 36 万个样本，包括每次溢出复位前后，加速度模长都在 0.8–1.2 g 之内。唯一的例外是长测 L1：30 万个样本里有 4 个超出范围。FIFO 读错位会让之后的数据一直错下去，直到下次复位，不会只影响零星几个样本。为了区分，测试程序改为打印异常样本的原始值，并在同样条件下复跑（L3 为 v5，L4 为 v3，各 5 分钟，期间不碰板子），两组都是 0 个。所以 L1 那 4 个样本的原因没能确认，最可能是测试期间板子受到了晃动。

## 过程中遇到的问题

| 问题 | 原因 | 解决 |
|---|---|---|
| 模块加载报 `__aeabi_ldivmod` 未定义 | 32 位 ARM 内核没有 64 位除法的库函数，`s64 / int` 会被编译器转成这个调用 | 用 `div_s64()`、`div64_u64()` |
| v3 卸载不掉（`rmmod` 报模块正在使用） | v3 把自己的触发器设为默认触发器，4.1 的 `iio_trigger_get()` 同时 `__module_get()` 本模块 | 卸载前 `echo "" > trigger/current_trigger`（测试脚本已处理）。v5 没有触发器，不存在这个问题 |
| 实时任务占用时统计出假的丢样 | 时间戳窗口只用了读完计数后的时刻 | 读计数前后各取一次时间（分析第 3 条） |
| 重负载下偶发一次溢出 | 推断为 SPI 消息泵优先级反转 | 消息泵改为实时优先级，未能复现（分析第 4 条） |

## 局限

- 没有水位中断，只能定时读：缓冲区打开期间，即使芯片还没攒够，线程也按周期醒来。
- 时间戳是推算值。需要每个样本的精确时刻时，可以只开数据就绪中断用来计时，或换用有 FIFO 水位中断的型号（ICM-20602）。
- 关闭缓冲区时，FIFO 里不足一批的样本被丢弃（最多 watermark 个）。
- 没有实现 `hwfifo_flush_to_buffer`（让 read 当场从 FIFO 取数）：读取线程已经保证数据最多晚一个批周期到达，而且这个回调在 4.1 里是在 `wait_event` 的条件判断中调用的，带睡眠的 SPI 读放在那里并不合适。
